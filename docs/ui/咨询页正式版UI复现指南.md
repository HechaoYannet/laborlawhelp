# 咨询页正式版 UI 复现指南

本文档用于把当前“演示模式”中验证过的咨询页 UI，整理为可直接在正式版复现的工程规范。

目标是：正式版仍然保留同样的聊天式信息收集、结构化结果卡、文书生成、律师分流与总结回顾能力，但不再依赖 `demo` query、固定脚本或硬编码案情。

## 1. 复现目标

正式版咨询页应满足以下目标：

1. 用户进入后先看到清晰的案型入口或咨询引导，而不是空白输入框。
2. 问诊过程采用聊天式交互，围绕劳动争议事实逐步收集信息。
3. 完成提问后，在同一聊天界面内展示 4 张结构化结果卡：
   - 要素抽取与案情摘要
   - 测算赔偿项目
   - 文书生成
   - 繁简分流与律师转介
4. 结果卡必须是可交互 UI，不使用纯文本长段落替代。
5. 文书生成和律师转介必须是真实的前端动作闭环，不是演示占位。
6. 页面结构必须符合项目现有规范：Next.js App Router、shadcn/ui 风格组件、Tailwind CSS、TypeScript strict。

## 2. 必须抛弃的演示模式依赖

正式版禁止保留以下依赖：

1. `?demo=dismiss` 之类的 query 开关。
2. 固定问答脚本返回值。
3. 硬编码案情数据直接写入咨询流程。
4. 依赖消息文案判断“是否是演示步骤”的字符串分支。
5. 任何仅用于演示的占位消息，例如“演示模式”“硬编码对话”“演示结果卡”。
6. 中间件失败时自动拼接本地规则回复作为主链路输出。

正式版可以保留的是：

1. 聊天消息流的 UI 结构。
2. 结构化结果卡的交互模式。
3. 文书输出卡和律师卡的展示形态。
4. 左侧摘要、时间线、待办、材料包这类辅助面板。

## 3. 页面结构

正式版咨询页推荐采用以下布局：

1. 顶部 Header：平台名、当前咨询类型、会话状态。
2. 左侧信息面板：案情摘要、进度、时间线、待办、材料包。
3. 中央消息区：用户提问、AI 回复、生成中的状态、结果卡、文书卡、律师卡。
4. 底部输入区：文本输入、语音输入、发送按钮、快捷示例。

推荐的视觉层级：

1. 聊天内容始终是主区域。
2. 结构化结果卡是 AI 收官输出的一部分，嵌在消息流中，不跳出页面。
3. 辅助面板仅用于帮助用户理解进度，不替代主对话。

## 4. 组件拆分建议

正式版建议把当前页面拆成以下组件：

1. `ConsultationPageShell`
   - 负责整体布局、桌面/移动端适配、侧边栏收起展开。
2. `ConsultationConversation`
   - 负责消息流渲染、打字中状态、用户/AI 气泡、结果卡插入位。
3. `ConsultationComposer`
   - 负责输入、语音、发送、快捷模板。
4. `ConsultationSidebar`
   - 负责摘要、时间线、待办、材料包。
5. `ConsultationResultCards`
   - 负责 4 张结构化结果卡的切换、展开、复制、动作按钮。
6. `DocumentPreviewPanel`
   - 负责文书生成后的预览、复制、下载、继续编辑。
7. `LawyerReferralPanel`
   - 负责律师推荐列表、转介动作、复制摘要、在线预约入口。

当前仓库里的 `src/app/consultation/page.tsx` 可以作为这套拆分的参考实现，但正式版应当把逻辑继续下沉，避免单页承担过多职责。

## 5. 状态流设计

正式版的状态建议分为 5 层：

1. 会话状态
   - 当前消息列表、输入内容、是否正在思考、是否可滚动到底部。
2. 案情状态
   - 结构化案情字段、提取出的事实、时间线、证据列表。
3. 结果状态
   - 计算结果、文书结果、律师推荐结果、分流结果。
4. UI 状态
   - 侧边栏收起、移动端键盘偏移、当前激活卡片、复制状态。
5. 交互状态
   - 文书是否已生成、律师卡是否已推送、是否已完成当前阶段。

建议把这些状态放在以下层级：

1. `useCaseStore` 保存跨消息流共享的案情、文书、分流与律师推荐结果。
2. 页面本地 `useState` 只保存纯 UI 状态，例如展开收起、复制提示、当前卡片。
3. 领域规则与模板函数放在 `src/lib/*`，不要写在页面中。

## 6. 交互流程

正式版对话流程建议按以下顺序实现：

### 6.1 开场

1. 用户进入咨询页。
2. 页面展示平台定位和一个明确的起始引导。
3. 用户可以通过快捷问题或直接输入开始咨询。

### 6.2 多轮问诊

1. AI 根据当前案情追问缺失字段。
2. 每轮问题聚焦一个事实点：劳动关系、工资、合同、辞退方式、辞退理由、社保、交接、维权进度等。
3. 用户回答后立即更新摘要和时间线。

### 6.3 结果收官

1. 当关键字段齐备后，AI 在同一消息流中输出 4 张结果卡。
2. 结果卡不是文本摘要，而是可交互 UI。
3. 卡片内部可以切换、复制、生成文书、推送律师卡。

### 6.7 中间件卡片协议（正式版）

正式版前端必须按中间件 SSE 输出的结构化字段渲染卡片，不再依赖本地文本拆解：

1. 使用 `tool_result` 事件中的以下字段：
   - `card_type`
   - `card_title`
   - `card_payload`
   - `card_actions`
2. 兼容策略：若缺失 `card_*` 字段，才回退为工具摘要文本展示。
3. 四类卡片的默认映射：
   - `fact_summary` -> 要素抽取与案情摘要卡
   - `compensation` -> 测算赔偿项目卡
   - `document` / `case_summary` / `action_checklist` / `arbitration_application` -> 文书生成卡
   - `lawyer_referral` -> 繁简分流与律师转介卡

### 6.4 文书生成

1. 用户点击“生成文书”。
2. 前端调用文书生成函数，得到仲裁申请书、证据目录、行动清单等结构化结果。
3. 页面展示文书预览卡，并提供复制或下载入口。

### 6.5 律师转介

1. 用户点击“推送律师卡片”。
2. 前端调用分流评估与律师推荐函数，生成推荐列表。
3. 页面展示律师卡片，提供复制摘要、预约或转发动作。

### 6.6 总结回顾

1. 左侧面板或收官卡展示本次咨询的摘要、流程、待办。
2. 用户可以快速复制整份会话总结给律师或继续追问。

## 7. 结果卡的正式版规范

结果卡要满足以下标准：

1. 每张卡必须有标题、摘要、结构化字段和说明。
2. 卡片内容要直接来自结构化数据，不从纯文本拆片段。
3. 卡片按钮要真实可用，不做视觉占位。
4. 卡片可折叠、可切换、可复制。
5. 文书卡和律师卡必须支持后续动作。

推荐的四张卡内容：

1. 要素抽取与案情摘要
   - 劳动关系起止
   - 工资口径（税前/到手）
   - 辞退方式与理由
   - 社保与证据情况
2. 测算赔偿项目
   - 工作年限
   - 月工资基数
   - 赔偿金额
   - 额外主张项目
3. 文书生成
   - 仲裁申请书
   - 证据目录
   - 行动清单
4. 繁简分流与律师转介
   - 复杂度
   - 风险等级
   - 口径风险
   - 律师推荐

## 8. 文书生成接入规范

正式版文书生成应遵循以下规则：

1. 只通过 `src/lib/document-generator.ts` 生成文书，不把模板拼接写在页面里。
2. 页面只负责传入 `CaseProfile`、`CalculationResult` 等数据。
3. 文书结果要落到 `useCaseStore`，便于后续复制、导出、转介。
4. 文书预览应采用独立卡片，不直接用长段落堆叠。

建议正式版文书输出至少包含：

1. 劳动仲裁申请书草稿。
2. 证据目录。
3. 维权行动清单。

## 9. 律师转介接入规范

正式版律师转介应满足以下条件：

1. 通过 `src/lib/case-triage.ts` 生成复杂度与推荐结果。
2. 律师卡必须展示律所、专长、信誉、联系方式等摘要信息。
3. 转介动作必须能把案情摘要传给律师端口或复制给用户。
4. 用户应能从同一界面发起预约或转发。

## 10. 视觉与样式规范

正式版 UI 应符合项目现有开发规范：

1. 使用 shadcn/ui 组件作为基础。
2. 使用 Tailwind CSS 类名完成布局与状态样式。
3. 避免 inline style。
4. 避免把页面做成通用后台默认风格，卡片层次要明确。
5. 桌面与移动端都要可用，横屏/窄屏状态都要考虑。
6. 文书卡、律师卡、摘要卡要保持统一圆角、阴影、间距节奏。

建议的视觉策略：

1. 主消息流保持白底或浅色内容容器。
2. 结果卡使用更明显的色块区分不同功能。
3. 关键动作按钮使用实心或高对比样式。
4. 同一页只保留一个主视觉焦点，不要同时堆很多强调色。

## 11. 正式版复现步骤

如果要在正式版完整复现当前 UI，建议按以下顺序实施：

1. 抽出页面壳层。
2. 抽出聊天消息流组件。
3. 抽出结果卡组件。
4. 抽出文书预览组件。
5. 抽出律师转介组件。
6. 用真实案情输入和规则引擎替代 demo 固定数据。
7. 接入正式版会话状态和服务端数据源。
8. 删除 demo 开关、固定脚本和演示文案。

## 12. 验收标准

正式版达到以下标准即可认为复现完成：

1. 用户在咨询页内可以完成一轮完整问诊。
2. 问诊结束后出现 4 张结果卡。
3. 文书卡可生成并展示真实文书结果。
4. 律师卡可推送并展示推荐律师结果。
5. 页面无需依赖演示模式即可运行。
6. `pnpm build` 通过。
7. 代码拆分符合项目规范，页面逻辑不过度膨胀。
8. `tool_result` 扩展卡片字段能在消息流内触发结构化卡片渲染。

## 13. 备注

当前仓库中的演示实现仅作为这份规范的验证样板。正式版实现时，应保留 UI 结构与交互模式，去掉所有 demo 相关开关与硬编码脚本。
